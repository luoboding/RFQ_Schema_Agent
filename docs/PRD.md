# RFQ Schema Agent 产品需求文档（PRD）

**版本**：v1.0  
**日期**：2026-10-19  
**状态**：草案  
**关联项目**：ForgeFlow 采购邮件代理（比价 Agent 体系）  
**目标读者**：工程团队、产品负责人

## 1. 背景与问题

ForgeFlow 是一个面向采购与寻源团队的本地优先（local-first）邮件 AI 助手。买方将 ForgeFlow 抄送在发出的询价邮件（RFQ）中，它自动处理供应商回复、提取报价数据、并在信息缺失时起草跟进邮件，循环往复直到每份 RFQ 信息完整。

ForgeFlow 采用三 Agent 协作架构。操作规则很简洁：**买方的 RFQ 创建“表单”，供应商回复填充“表单”，Action Agent 判断还缺什么。**

本 PRD 聚焦第一个 Agent：**RFQ Schema Agent**。它的职责是：**读取买方发出的原始 RFQ 邮件，为该邮件线程创建并持久化一份动态的“采集表单”（collection form），作为后续所有提取和完整性判断的唯一事实来源**。

**没有这个 Agent，后续的提取和跟进就失去了比对基准。** 它是整个比价 Agent 体系的地基。

## 2. 产品目标

| 目标 | 衡量方式 |
|------|---------|
| 从 RFQ 邮件中自动推导出结构化的必填字段清单 | 人工对比 Agent 输出与邮件实际需求，字段召回率 ≥ 95% |
| 生成的表单能被 Extraction Agent 和 Action Agent 直接消费 | 下游 Agent 无需人工干预即可基于表单执行提取和完整性判断 |
| 表单持久化到邮件线程，多轮回复中保持一致 | 同一线程内重复调用 Schema Agent 不产生不一致的表单 |
| 低置信度或缺失信息被显式标记，而非猜测 | 标记的缺失项在人工审核中确认率 ≥ 90% |

## 3. 用户与场景

**主要用户**：采购员（Buyer）

**触发场景**：
1. 采购员向一个或多个供应商发送 RFQ 邮件，将 ForgeFlow 抄送（CC）。
2. ForgeFlow 检测到 CC 中的自身地址，触发 RFQ Schema Agent。
3. Schema Agent 读取该邮件，生成采集表单，绑定到邮件线程 ID。

**用户价值**：采购员不需要手动定义“这次询价需要供应商报什么”。Agent 从 RFQ 原文中自动推导，采购员只需在仪表板上确认或微调。

## 4. 功能需求

### 4.1 输入

| 输入项 | 说明 | 必填 |
|--------|------|------|
| 买方 RFQ 邮件正文 | 纯文本/HTML，包含询价描述 | 是 |
| 邮件主题 | 用于辅助判断 RFQ 类型 | 是 |
| 附件（如有） | 如 BOM 表、图纸、规格书 | 否 |
| 供应商列表 | 从收件人/抄送中推导 | 是（用于绑定） |
| 邮件线程 ID | 用于持久化表单 | 是 |

### 4.2 核心处理逻辑

**步骤 1：RFQ 内容解析**
Agent 读取买方 RFQ 邮件，识别其中隐含或显式的采购需求。需要识别的信息类型包括：
- 物料/零件描述（名称、规格、型号）
- 数量或数量范围
- 期望交期
- 目标价格（如有）
- 特殊要求（如材质、认证、包装）

**步骤 2：必填字段推导**
基于解析结果，Agent 生成该 RFQ 的**动态采集表单**。表单字段不是固定的，而是从 RFQ 内容中推导出来的。参考 ForgeFlow 从供应商回复中提取的字段类型，表单至少应覆盖以下候选字段（按需启用）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `unit_price` | 数值 + 币种 | 单价，支持价格阶梯 |
| `price_tiers` | 数组 | 如 `100@$24.00, 500@$18.00` |
| `lead_time_weeks` | 数值 | 生产交期（周） |
| `long_lead_parts` | 字符串数组 | 交期 ≥ 8 周的零件号 |
| `moq` | 数值 | 最小起订量 |
| `payment_terms` | 字符串 | 如 `Net 30` |
| `nre` | 数值 + 币种 | 一次性工程费用 |
| `coo` | 字符串 | 原产国（用于到岸成本计算） |
| `quantity` | 数值 | 供应商实际可报价数量（可能与 RFQ 不同） |

**步骤 3：字段必要性判定**
并非所有候选字段都是必填的。Agent 根据 RFQ 内容判断哪些字段是该 RFQ 的**必需采集项**：
- 如果 RFQ 明确要求报价，`unit_price` 必填。
- 如果 RFQ 提到“请报交期”，`lead_time_weeks` 必填。
- 如果 RFQ 提到“包含模具费”，`nre` 必填。
- 如果 RFQ 未提及某字段，该字段标记为**可选**。

**步骤 4：置信度标注与不确定性暴露**
Agent 对每个推导出的字段标注置信度（高/中/低）。对于**低置信度**的判定（例如 RFQ 中“尽快”是否意味着交期是必填项），Agent 不应自行决定，而是标记为**待人工确认**，并在仪表板中提示采购员。

**步骤 5：表单持久化**
生成的采集表单绑定到邮件线程 ID，写入持久化存储。后续同一线程的所有供应商回复，都基于同一份表单进行提取和完整性判断。

### 4.3 输出

**主输出**：一份结构化的 `RFQCollectionForm` 对象，包含：

```json
{
  "thread_id": "string",
  "rfq_summary": "string",
  "suppliers": ["vendor_a@example.com", "vendor_b@example.com"],
  "required_fields": ["unit_price", "lead_time_weeks", "moq"],
  "optional_fields": ["payment_terms", "coo"],
  "field_definitions": {
    "unit_price": {"type": "number", "currency_required": true},
    "lead_time_weeks": {"type": "number", "unit": "weeks"},
    "moq": {"type": "number", "unit": "pieces"}
  },
  "low_confidence_decisions": [
    {"field": "nre", "reason": "RFQ mentions 'tooling cost' but unclear if one-time", "suggested_action": "confirm_with_buyer"}
  ],
  "created_at": "ISO8601"
}
```

**副输出**：在仪表板中展示的表单预览，供采购员审核。

## 5. 非功能需求

| 需求 | 要求 |
|------|------|
| 延迟 | 从触发到表单持久化完成，P95 < 30 秒 |
| 准确率 | 必填字段推导的精确率 ≥ 90%（人工抽检） |
| 本地优先 | 表单数据及 RFQ 内容不离开本地存储；仅发送给 AI 模型的必要文本片段除外 |
| 幂等性 | 同一 thread_id 重复调用不覆盖已确认的表单，返回已有版本 |
| 可审计 | 每次生成的表单及其推导依据（邮件原文片段）应可追溯 |

## 6. 边界与约束

**Agent 不做的事**：
- **不做价格计算或比价**。那是应用层的确定性逻辑。
- **不替代采购员做最终判断**。低置信度决策必须暴露给人工。
- **不修改买方原始 RFQ 邮件**。
- **不生成发给供应商的跟进邮件**。那是 Action Agent 的职责。

**已知限制**：
- 如果 RFQ 邮件内容极其模糊（如“报个价”无任何细节），Agent 将输出大量低置信度标记，需采购员手动补充表单。
- 附件解析能力取决于后续迭代，v1 优先处理邮件正文。

## 7. 与其他 Agent 的接口

| 下游 Agent | 消费的 Schema Agent 输出 | 用途 |
|-----------|------------------------|------|
| Supplier Extraction Agent | `required_fields`, `field_definitions` | 指导从供应商回复中提取哪些字段 |
| RFQ Action Agent | `required_fields`, 当前提取结果 | 判断哪些必填字段仍缺失，决定是否起草跟进邮件 |

## 8. 成功指标（上线后 4 周评估）

| 指标 | 目标 |
|------|------|
| Schema Agent 生成的表单被 Action Agent 直接采用的比例（无需采购员手动修改） | ≥ 80% |
| 因 Schema Agent 漏判必填字段导致跟进邮件遗漏的比率 | < 5% |
| 采购员对表单预览的平均审核时间 | < 15 秒/RFQ |
| 同一线程多轮回复中表单一致性（无意外变更） | 100% |

## 9. 开放问题

1. **附件处理**：BOM 表格中的物料清单是否应自动纳入表单的 `required_fields`？建议 v1 仅做标记提示，v2 再实现结构化提取。
2. **多供应商差异化**：如果不同供应商收到的 RFQ 内容有细微差异（如 A 供应商收到完整版，B 供应商收到简化版），表单应按线程统一还是按供应商区分？建议 v1 按线程统一，简化实现。
3. **表单版本化**：采购员手动修改表单后，是否需要保留原始 Agent 生成的版本用于审计？建议保留，但不在 UI 中默认展示。

**附录：参考依据**

本 PRD 的架构设计基于 ForgeFlow 开源项目的三 Agent 模式及 RFQ Schema Agent 的职责定义。供应商报价字段清单参考 ForgeFlow 从报价邮件中提取的字段类型。本地优先部署与人在回路原则与 ForgeFlow 的整体设计一致。
